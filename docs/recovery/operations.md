# Recovery and resilience operations

## Scope and ownership

The operator owns backup schedules, encrypted off-host storage, access control, retention, monitoring, restore drills and incident decisions. A backup contains sensitive Identity and session data even when refresh tokens are stored as hashes. Protect backups and their encryption keys separately, test access to both, and never put passwords, connection strings, tokens or keys in commands, tickets or logs. Inject secrets from an external secret manager with narrowly scoped identities; environment variables are visible to privileged processes and are not a vault. Database backups do not contain the external secret manager, JWT signing keys, IdP configuration, Redis state, ingress configuration or deployment artifacts; back up and recover these independently under their own policies.

Define an RPO and RTO with the service owner before deployment. A full backup or PostgreSQL logical dump alone recovers to its snapshot, not the time of failure. Measure the age of the last usable backup and include detection, decision, provisioning, transfer, restore, integrity checks, security reconciliation and cutover in RTO. For smaller RPOs design and test SQL Server log backups/recovery model or PostgreSQL physical backup plus WAL archiving and point-in-time recovery separately. Neither PITR nor production RPO/RTO is established by the exercise below. Monitor backup success, age, storage, restore errors and restore duration; successful backup creation alone is not proof of recoverability.

Starting proposal, not an established SLA: the service owner approves RPO 24 hours and RTO 8 hours after a measured drill; the database operations owner schedules daily full backups and quarterly isolated restore drills, retains 14 daily and 12 monthly encrypted copies off-host, and tests separate key recovery. Security owns key custody and access review. Adjust to business impact, legal requirements and actual restore duration; snapshots alone cannot satisfy a shorter RPO. These values are not implemented or promised by this template.

SQL Server database backups do not restore server-level logins and their SIDs, server configuration, certificates or external encryption keys. Inventory and securely recover these separately, preserving login SIDs and validating database user mappings and TDE/backup certificate private keys. Coordinate with the database owner: ad-hoc full backups should use `COPY_ONLY` so they do not change the differential base; log backup strategy and recovery chain remain operator responsibilities.

## Incident procedure

1. Declare an incident, identify the authoritative primary, stop or fence application writes, background jobs and other writers, and preserve evidence. Record the intended recovery point and data-loss window. Never overwrite the only surviving copy. Prevent traffic reaching an unverified target.
2. Choose a known-good backup and compatible engine/version and schema. Restore to a **separate, access-restricted** target with adequate capacity. For SQL Server use `RESTORE VERIFYONLY ... WITH CHECKSUM` where the backup supports it, then `RESTORE DATABASE ... WITH MOVE` for each logical data/log file and run `DBCC CHECKDB`. For PostgreSQL a custom-format `pg_dump` archive can be restored to an empty database using `pg_restore --exit-on-error`; assess ownership, extensions, collations and database-level privileges separately. PostgreSQL logical dumps do not include cluster-global roles; restore or provision them independently. The exercise uses `--no-owner --no-privileges`, not a production grant policy. Native physical/PITR recovery has a different procedure and must be rehearsed separately.
3. Check migration history against the deployed application, database integrity, representative business and Identity records, constraints and a controlled write on the isolated target. Reconcile lost writes and external side effects from authoritative records; do not blindly replay requests whose result is unknown. Review runtime database principals and least privilege using [deployment operations](../database/deployment-operations.md). Verify replicas and read routing; readiness checks connectivity, not schema correctness.
4. **Before exposing the target**, treat restored security state as stale. A restore can resurrect manual role assignments, external grants, linked logins, accounts and refresh hashes revoked after the backup. Review and reconcile all of these against authoritative administrative and IdP records, including grant expiration and the possibility that still-valid external tokens can reassert privileges. Do not assume a prior revocation survived. See [role ownership](../security/role-ownership-and-revocation.md).
5. Invalidate all restored refresh sessions/families using an audited, tested administrative procedure while writers are fenced. Account for legacy tokens without a family as well as family-backed tokens; changing signing keys alone is not a substitute for removing/revoking restored refresh state. Rotate local JWT signing keys and remove old validation keys when immediate access-token invalidation is required, coordinating every instance and client. Retaining old validation keys permits previously issued access tokens until expiry; forced rotation logs users out and requires coordinated secret distribution. External IdP tokens and keys require separate IdP action. Verify denial of old tokens and reauthentication before cutover; the template does not provide a complete recovery invalidation command.
6. Recreate or validate external secrets and configuration, run controlled authentication/authorization and business smoke checks, then switch traffic in a coordinated manner. Monitor errors and privilege changes, document the data-loss window and decisions, and retain the old target until incident policy permits disposal.

## Failure and shutdown behavior

Permission decisions read the primary database, not Redis and not JWT role claims. Redis does not cache permissions; authorization database failures propagate rather than granting access via a stale fallback. In-flight requests are not retroactively revoked. Redis failures may affect features using the configured cache and must be monitored; do not interpret them as permission grants or assume an automatic fallback. See [role ownership](../security/role-ownership-and-revocation.md).

`RedisCacheService.GetOrSetAsync` propagates a failed/canceled get without invoking the factory; a failed/canceled set happens after one factory invocation and propagates without retry. The operation is not single-flight: concurrent callers and later attempts can invoke the factory again. Factories must be read-only/idempotent, never perform side effects or represent exactly-once work. A cache failure is not a safe reason to replay an ambiguous write. Existing `InternalAuthorizationTests.PermissionStoreFailure_DoesNotFallBackToSignedTokenRoles` tests fail-closed authorization.

Set and test connection, command, proxy and shutdown timeouts for the deployment and provider, propagate cancellation, stop accepting traffic before terminating instances, and allow in-flight requests and hosted services a bounded drain period. Readiness timeouts are cooperative, not a hard deadline for an uncooperative provider; liveness is independent of external services. Do not abandon scoped resources in the background. Retry only operations known to be safe/idempotent with bounded backoff and cancellation. Never automatically retry an ambiguous write or refresh rotation: a timeout can occur after commit; reconcile its outcome instead. Provider-specific transactional retries have their own limited contracts and do not authorize generic write retries.

The cleanup background service awaits each database command before disposing its scoped context. Its two deletes are separate statements, not a transaction: cancellation between them can leave the first committed. The cooperative blocked-first-command test proves that specific command does not write and stop waits for it, not atomicity of the complete cleanup. Subsequent cleanup can process remaining eligible rows.

### Timeout inventory and proposed budget

These are **starting proposals**, not currently configured service guarantees. Measure under load and ensure ingress/client deadlines exceed the selected operation budgets. Provider and framework defaults depend on package versions and connection strings; inspect the actual deployment rather than assuming an imposed global deadline.

| Path | Current source / setting | Proposed starting point and how to apply |
| --- | --- | --- |
| SQL Server / PostgreSQL connection | `ConnectionStrings:DefaultConnection` and optional `ProductReadReplica`; no explicit timeout in registration. Default depends on provider, version and connection string. | 5 s using provider connection-string `Connect Timeout=5` (SQL Server) or `Timeout=5` (Npgsql); validate network and pool behavior. |
| EF / Dapper commands | No EF command timeout configured; Dapper commands do not set one. Defaults depend on provider, version and connection string; SqlClient 7.1.1 documents 30 s. | 10 s as provider default using `Command Timeout=10` in the SQL Server or Npgsql connection string. EF provider `CommandTimeout(10)` or a Dapper `CommandDefinition` command timeout can override the provider default and require application changes; no dedicated template configuration key exists. Do not assume connection timeout limits commands. Readiness sets its own command timeout. |
| Redis | `Caching:Redis:ConnectionString`; timeout defaults depend on client version and configuration; no cache fallback. | 2 s connection and async/sync operations via supported connection-string `connectTimeout=2000,asyncTimeout=2000,syncTimeout=2000`; verify client/version behavior and retry policy. |
| OIDC metadata / keys HTTP | JWT bearer backchannel uses framework defaults; template sets authority, not an HTTP timeout. Defaults depend on framework version. Cached metadata and refresh behavior affect requests. | 5 s backchannel, requiring `JwtBearerOptions.BackchannelTimeout` configuration in code; no template key exists. Test IdP outages and key rollover. |
| OTLP export | `OpenTelemetry:Otlp:Endpoint` and protocol configured explicitly; exporter timeout depends on SDK version and configuration, not a template key. | 5 s using SDK-supported `OTEL_EXPORTER_OTLP_TIMEOUT=5000` where honored by installed SDK, verify actual exporter configuration. Export is best effort, not request durability. |
| Readiness | `HealthChecks:TimeoutSeconds` default 5, validated 1–60; also sets DB probe command timeout. | 3 s via `HealthChecks__TimeoutSeconds=3`; orchestrator probe timeout must accommodate it. Cancellation remains cooperative, not a hard bound. |
| Host shutdown | Generic Host `HostOptions.ShutdownTimeout`; no explicit binding in this template. Default depends on framework version and host configuration. | 30 s via real host configuration key `shutdownTimeoutSeconds` (e.g. `DOTNET_SHUTDOWNTIMEOUTSECONDS=30`); verify host configuration for the deployment. Increase orchestrator termination grace to at least 45 s plus ingress drain. |

Local sources checked: `Directory.Packages.props` pins `Microsoft.Data.SqlClient` 7.1.1; the installed `<NuGet package cache>/microsoft.data.sqlclient/7.1.1/ref/net9.0/Microsoft.Data.SqlClient.xml`, member `SqlConnectionStringBuilder.CommandTimeout`, documents the connection-string builder property and its 30-second default. `src/CleanTemplate.Infrastructure/Extensions/ServiceCollectionExtensions.Persistence.cs` registers the database providers without an EF command timeout; `src/CleanTemplate.Infrastructure/Repositories/Reads/ProductReadRepository.cs` creates Dapper commands without one. `src/CleanTemplate.Host/Health/DatabaseHealthCheck.cs` explicitly sets the probe command timeout. Verify effective settings and any overrides in the deployed version and connection strings.

For SIGTERM (Linux/orchestrator) or Windows service stop, first remove the instance from ingress and allow connection/endpoint propagation (e.g. 10 s, measured), then request host shutdown. Configure the external termination grace to include drain plus host timeout; HostOptions is a cooperative cancellation budget, not a guarantee that uncooperative code or a killed process completes. Await hosted work and scoped resource disposal; never abandon a command via `WaitAsync`. A hard kill can interrupt writes and telemetry; reconcile unknown outcomes. Windows service control and hosting integration must be configured by the deployer; ordinary console termination behavior is not a substitute for testing service stop.

## Reproducible isolated drill

From the repository root, with Docker running, PowerShell and .NET 10 installed:

```powershell
pwsh -NoProfile -File scripts/tests/Test-BackupRestore.ps1
```

The default runs SQL Server 2022 Developer then PostgreSQL 17 sequentially; `-Provider SqlServer` or `-Provider PostgreSql` selects one. Images may need downloading. The script creates random containers with loopback-only random host ports and random process-environment passwords; it does not accept or touch user databases. It creates its own source and separate target databases, applies actual provider EF migrations, and populates a versioned product, Identity user, manual role, linked login, external grant, refresh family and representative hash. It makes a native SQL Server `BACKUP DATABASE` with COPY_ONLY and checksum or `pg_dump -Fc`, copies the archive through a unique ignored `work/recovery-<random>` directory, mutates the source, and restores the copied archive with `RESTORE DATABASE ... WITH MOVE` or `pg_restore` into the target. It checks migration history, representative records, version and hash, post-backup absence/revocation rollback, and a subsequent persisted versioned write. SQL Server also runs `RESTORE VERIFYONLY` and `DBCC CHECKDB`; PostgreSQL restore errors and application checks are not equivalent to a physical consistency check.

Cleanup in `finally` removes only the created container and its unique verified work directory, and restores process environment variables. Abrupt process or host termination can prevent cleanup: inspect the `clean-template-test=recovery` label and `work/recovery-*` before manually removing only resources belonging to the interrupted run. Do not publish archives or environment dumps. The script uses privileged test database accounts solely inside disposable containers.

## Evidence and limits

On 2026-11-03, `Test-BackupRestore.ps1` completed in Release against both Docker engines sequentially, with seed, mutate and verify each passing (one filtered acceptance test per phase per engine). SQL Server checksum verification and `DBCC CHECKDB` completed; PostgreSQL custom dump and restore completed with `--exit-on-error`. Following the change adding SQL Server `COPY_ONLY`, the SQL Server drill was rerun successfully, including all three phases and checks. The exercise demonstrates restoration to a separate database on the **same disposable engine instance**, not host/site disaster recovery, external secrets recovery, real production data, real IdP, production privileges, physical PostgreSQL checks, PITR, HA/failover, or security invalidation. It deliberately demonstrates that a revoked hash and deleted grants reappear. It does not measure or promise production RPO/RTO. Run deployment-specific drills independently.
